# Progress notes: table detection + bowl placement + scan pose

Session: evening of Sep 28 to early Sep 29, 2026, on `rchi-cpu-5` (Kinova Gen3 7-DOF arm with a RealSense wrist camera, arm plugged directly into this machine).
Code: `~/walter_table`, git commit `6fe26a0` ("Table detection, bowl placement, scan pose").

## Summary

- Built a perception pipeline that finds the table in one depth image, then finds a clear spot on it where a bowl can be set down.
- Ran it live on the robot's wrist camera as a ROS 2 node.
- Added a fixed "scan pose" so the arm moves to a spot where the camera sees the whole table before detecting.
- Ran the whole thing (move, then detect, then show the result) from one command on the real arm, and it worked.

## 1. Table detection (`table_detect.py`)

- Turns each depth pixel into a 3D point, then finds the table as the largest roughly horizontal plane, using RANSAC.
- Reports the table's height, tilt and center, and draws the table in red on the color image.
- Needs only numpy and scipy. Open3D is optional.

## 2. Bowl placement: finding free space on the table

- Looks at the table from directly above and splits it into a 5 mm grid. Each square is marked as one of:
  - **free:** bare tabletop is visible there;
  - **occupied:** something 1–40 cm tall is standing there;
  - **unknown:** nothing was measured, for example past the table edge or in the shadow behind an object. Unknown squares count as blocked, so the bowl is never placed on a blind spot.
- For every free square, it works out the distance to the nearest blocked square, using scipy's distance transform.
- The bowl has to keep two different gaps:
  - from objects: bowl radius + 2 cm;
  - from the table edge: bowl radius + 8 cm, so the bowl isn't set down where it could tip off.
- Of all the spots where the bowl fits, it picks the one nearest the middle of the camera's view. If none fits, it says why.
- Default settings: bowl radius 5.5 cm, object gap 2 cm, edge gap 8 cm, 5 mm grid. All four can be changed from the command line or as ROS parameters.
- **Tests:** `test_placement.py` has 10 offline tests, and all 10 pass. They cover:
  - staying clear of objects and edges;
  - several object layouts;
  - a crowded table correctly returning "no room";
  - a bare table placing near the center of the view;
  - a bigger bowl moving the spot or giving up;
  - both gaps being respected;
  - unknown space treated as blocked;
  - a speed check.
- **Real robot frame:** `robot_color.png` / `robot_depth.png` are a frame from the wrist camera, and `robot_overlay.png` is the detector's output on it:
  - the table is correctly red;
  - the object on the table and the background clutter are yellow;
  - the green bowl circle is in the open area, away from the object and the edges.

## 3. Live ROS 2 node (`table_detector_node.py`)

- Runs the detector at 2 Hz on the wrist camera's `/camera/wrist/...` topics.
- Publishes an overlay image (`/table_detector/overlay`) and RViz markers (`/table_detector/marker`): a red slab for the table and a green disc for the bowl spot.
- If there's no transform between the camera and the arm base, it falls back to "largest plane". That's the case on this machine right now (see Limitations).

## 4. Scan pose: moving the arm before detecting (`scan_pose.py`)

- **The pose:** chosen by looking through the camera and read off the Kinova web UI.
  - 0–360 form: J1–J7 = 353.787, 310.642, 181.649, 234.867, 2.240, 302.922, 91.168 deg.
  - Stored in the script in radians, each in [-π, π]: `[-0.10844, -0.86146, -3.11281, -2.18398, 0.03910, -0.99620, 1.59118]`.
- **Checked against the lab's existing arm code** (`~/feeding-deployment`, which I only read and never changed):
  - joint targets are sent as radians through `set_joint_position`, the same call the lab's `retract.py` preset uses;
  - the arm client talks to `arm_server.py` over TCP and needs no ROS;
  - on this machine the arm server runs locally (`127.0.0.1`), with no NUC;
  - bulldog is ROS 1 only, so on this machine `bulldog_bypass.py` stands in for it.
- **Safety checks:** the script refuses to move if any of these fail:
  - the arm server and bulldog bypass are running;
  - the speed preset is "low" (30°/s);
  - the gripper is open;
  - no joint would travel more than 150°.

  It also warns if a joint might spin the long way round, and waits for [ENTER] unless you pass `--yes`. `--dry-run` sends nothing.
- **Arrival check:** after the move it reads the joints back and reports failure if any joint is more than 1° off.
- **Safety trade-off:** with the bulldog bypass there is no software e-stop, so the physical e-stop is the only stop. One failsafe remains: if the bypass process dies, the arm e-stops within about 1 s.

## 5. One-command demo (`scan_and_detect.sh`)

- Moves the arm to the scan pose, then opens the overlay viewer and starts the detector, all in one terminal. Ctrl-C closes both.
- The detector only starts if the arm actually reaches the pose.
- This was for recording the demo video. It ran successfully on the real arm.

## Limitations and next steps

- **The bowl spot is only known in camera coordinates.** Nothing on this machine links the camera to the arm base, so the arm can't be sent to the spot yet. The next step is to bring up the arm's joint-state bridge and the saved wrist-camera calibration. `~/feeding-deployment` already has both for this arm: `feeding_deployment.ros2.joint_state_bridge`, `calibration_tf`, and `~/.ros2/easy_handeye2/calibrations/wrist_camera_calib.calib`.
- **The bowl radius (5.5 cm) should be measured on the real bowl.**
- **Test it on more tables, clutter and lighting.** So far it's been checked on one real frame plus the live demo.
- **Move speed** comes from the "low" preset, not a fixed 5 s duration, so bigger moves take longer.
- **The scan pose belongs to this arm and table setup.** If the table moves or you switch robots, re-record it.
- **Later:** move the code into `feeding-deployment` once the feeding pipeline actually uses it (for example, placing the bowl). Do it on a branch, after checking with the repo's maintainer. For now it stays in its own folder.

## How to run it again (on `rchi-cpu-5`)

```bash
# Terminals 1-3: arm stack (leave running). Physical e-stop is the only stop.
cd ~/feeding-deployment && export ARM_RPC_HOST=127.0.0.1
python3 src/feeding_deployment/control/robot_controller/arm_server.py   # terminal 1
python3 scripts/stub_base_server.py                                      # terminal 2
python3 scripts/bulldog_bypass.py                                        # terminal 3

# Terminal 4
cd ~/walter_table && export ARM_RPC_HOST=127.0.0.1
python3 ~/feeding-deployment/scripts/session/arm_set_speed.py low
python3 scan_pose.py --dry-run      # check the plan, nothing moves
./scan_and_detect.sh                # [ENTER] to move, then detection + viewer start
#   --yes skips the prompt; anything after it goes to the node, e.g.
#   ./scan_and_detect.sh --yes --ros-args -p bowl_radius:=0.055

# Offline, no robot needed
python3 test_placement.py
# The intrinsics below were copied from old notes and fit a 640x480 image, but robot_color.png
# is 1280x720. Use the real fx/fy/cx/cy from:
#   ros2 topic echo --once /camera/wrist/aligned_depth_to_color/camera_info
python3 table_detect.py --color robot_color.png --depth robot_depth.png \
    --fx 615 --fy 615 --cx 320 --cy 240 --depth-scale 1000 --largest-plane --out robot_overlay.png
```

To shut down, press Ctrl-C in terminal 3, then terminal 1, then terminal 2.
